## 1. 替换规则

| 规则 | 原文 | 替换后 | 依据 |
|---|---|---|---|
| R1 | 口令 | **密码** | 现有界面的全部用词：密码库、密码生成器、主密码、密码短语。混用会让用户以为「口令」和「密码」是两个不同的东西 |
| R2 | TOTP / OTP | **动态验证码** | 现有界面输入框占位文案就是「用于生成动态验证码」；TOTP 是技术缩写，不该出现在文案与需求叙述里 |
| R3 | 弱口令 / 强口令 / 空口令 / 明文口令 | **弱密码 / 强密码 / 空密码 / 明文密码** | R1 的复合词形态，逐条处理时不要只替换单字导致「弱密码」被漏掉 |
| R4 | 备份口令 / 测试口令 / 已知口令 | **备份密码 / 测试密码 / 已知密码** | 同上。注意：**口令原文（如 `BackupV1!fixture`）不替换**，只替换中文名词 |

**不做**：不替换代码标识符、不替换文件名、不替换 fixture 里的字符串值、不改历史修订记录。

## 3. 明确不能改的（改了会出错）

### 3.1 历史修订记录

`01-prd.md` 第 9 章 v0.1 ~ v0.6 各条**一律不改**，包括 299 行 v0.2 里的「口令含标题/用户名」。理由：修订记录记的是"当时写了什么"，回头改词等于篡改历史，以后没法用它对账。术语统一这件事由 v0.7 一行说明即可。

### 3.2 `05-copywriting.md` §0 术语表自身

13~15 行是「不要用」列，**必须保留** 口令 / TOTP / OTP / 双因素 / 2FA / MFA 这些被禁词——它们是被引用的反例，替换掉这张表就自毁了。执行时把 13~15 行加入白名单。

### 3.3 代码标识符与文件名

| 不替换 | 原因 |
|---|---|
| `TotpSecret`、`VaultMessages` 键名（`Health.*`） | 代码标识符，替换会破坏编译与映射 |
| `hello.blob`、`legacy-vault-v1.spv`、`legacy-vault-v1-backup.spvb`、`vault.spv` | 文件名 |
| `V1B-*`、`SEC-*`、`ROB-*`、`UX-*` | 需求编号 |
| 用例里的口令字符串 `VaultV1!fixture`、`BackupV1!fixture`、`NewVault!123` | 实际值 |

### 3.4 技术内部用词（非用户可见）

`落盘`、`凭据`、`派生密钥`、`AAD`、`AEAD`、`tag`、`nonce`、`salt`、`payload` 等只在需求/验收/设计里出现，不进入 UI。**不替换**——它们在工程语境里更精确，换成白话反而降低可验证性。

## 4. 三处需要你拍板（替换前定，否则会返工）

| # | 议题 | 现状 | 我的建议 |
|---|---|---|---|
| P1 | 左侧筛选标签「验证码」是否改成「动态验证码」 | 现有 UI 标签是 `验证码`（4 字，与 全部/登录/笔记 等宽），文案稿正文用「动态验证码」 | **不改标签**。标签位置窄，「动态验证码」5 字会挤；在术语表注明「标签=验证码，正文=动态验证码」，两者是简称与全称的关系，不构成混淆 |
| P2 | 「条目」与「账号」是否统一 | PRD 用「条目」（37 次），文案稿分组计数用「账号」（如 `{n} 个账号使用了弱密码`），汇总条用「条目」（`共 {n} 个条目需要处理`） | **不统一，两者语义不同**：条目含笔记与纯验证码记录，不可能都是"账号"；而弱密码/重复/长期未更新三组只可能来自登录类条目，用「账号」更贴近用户。**汇总条用「条目」是准确的**（因为体检总数包含笔记类），不要为了整齐把它改成「账号」 |
| P3 | 「加密备份」与「备份」混用 | PRD 两处词都用；文案稿用「加密备份」 | **用户可见文案统一「加密备份」**（强调是加密的，与非加密 CSV 区分）；需求/验收正文可保留「备份」简称，不影响判定 |
