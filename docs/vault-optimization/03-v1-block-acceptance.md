# 「v1 阻断五入口」验收用例清单

> 用途：SEC-03 的黑盒验收用例，供测试执行。**不含实现方案**，只描述「放什么、做什么、看什么、必须为什么假」。
> 对应的需求口径：`01-prd.md` 第 3 章 SEC-03、第 5 章 F5/F6、第 6 章 UI-1、第 7 章批次 A。
> 用例编号：V1B-01 ~ V1B-10（10 条）。
> 判定原则：**一条用例只有在「期望结果」全部成立且「反向断言」全部为假时才算通过**。提示文案正确但顺手写了一个备份文件，一律判失败。

---

## 1. 设计意图

v1 阻断类 bug 的典型形态不是「没提示」，而是「提示很正确，但顺手做了别的」：

| 典型形态 | 用户实际损失 | 本清单的拦截方式 |
|---|---|---|
| 提示"无法打开"，同时把 v1 文件复制成 `.corrupt-时间戳` | 目录被备份文件污染，用户误以为原库已损坏 | 目录文件清单比对（新增文件数必须为 0） |
| 提示"无法打开"，同时写了一个 `.tmp` 或新的空 `.spv` | 原库被覆盖或疑似损坏，数据链断裂 | 文件 SHA256 比对 + 文件长度比对 |
| 只堵住主窗口入口，扩展桥仍返回空密码 | 用户以为密码没了，实际是桥在撒谎 | 五入口逐个验证，桥必须返回显式错误 |
| 自动弹出"是否重建密码库"确认框 | 用户点"是"，库里数据当场没了 | 断言不出现任何要求用户处置旧文件的强制确认框 |

所以每条用例的反向断言都写成**可执行步骤**：先记录基线和哈希，再操作，再比对，而不是写"确认未修改"。

### 2.3 通用：记录基线（每条用例执行前跑一次）

```powershell
$root  = Join-Path $env:LOCALAPPDATA 'SnapFlow'
$work  = Join-Path $env:TEMP ('v1block-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
New-Item -ItemType Directory -Path $work -Force | Out-Null

function Get-VaultManifest {
    param([string]$Root)
    Get-ChildItem -LiteralPath $Root -Recurse -Force | ForEach-Object {
        if ($_.PSIsContainer) {
            [pscustomobject]@{ Rel = $_.FullName.Substring($Root.Length); Type = 'Dir';  Length = $null;         Sha256 = $null }
        } else {
            [pscustomobject]@{ Rel = $_.FullName.Substring($Root.Length); Type = 'File'; Length = $_.Length;     Sha256 = (Get-FileHash -LiteralPath $_.FullName -Algorithm SHA256).Hash }
        }
    }
}

Get-VaultManifest -Root $root | Export-Csv -LiteralPath (Join-Path $work 'before.csv') -NoTypeInformation -Encoding UTF8
Write-Host "基线已记录：$work\before.csv"
Write-Host ("vault.spv SHA256 = " + (Get-FileHash -LiteralPath (Join-Path $root 'vault.spv') -Algorithm SHA256).Hash)
Write-Host ("vault.spv 字节数 = " + (Get-Item -LiteralPath (Join-Path $root 'vault.spv')).Length)
```

**把上面两行输出抄进执行记录表**，不要只依赖 CSV（CSV 可能被覆盖）。

### 2.4 通用：反向断言（每条用例操作后跑一次）

```powershell
$root = Join-Path $env:LOCALAPPDATA 'SnapFlow'
$work = '<把 2.3 输出的目录粘进来>'

Get-VaultManifest -Root $root | Export-Csv -LiteralPath (Join-Path $work 'after.csv') -NoTypeInformation -Encoding UTF8

$before = Import-Csv -LiteralPath (Join-Path $work 'before.csv')
$after  = Import-Csv -LiteralPath (Join-Path $work 'after.csv')

# 断言 1：目录中没有新增任何文件或目录（新出现的路径必须为空）
$new = @($after.Rel | Where-Object { $before.Rel -notcontains $_ })
Write-Host ("新增路径数 = " + $new.Count)
$new | ForEach-Object { Write-Host "  [+ ] $_" }

# 断言 2：没有任何文件消失（消失同样是数据损失）
$gone = @($before.Rel | Where-Object { $after.Rel -notcontains $_ })
Write-Host ("消失路径数 = " + $gone.Count)
$gone | ForEach-Object { Write-Host "  [- ] $_" }

# 断言 3：关键文件哈希不变（log.txt 允许内容增长，单独放行）
$keys = @('\vault.spv', '\hello.blob', '\settings.json')
foreach ($k in $keys) {
    $b = ($before | Where-Object { $_.Rel -ieq $k }).Sha256
    $a = ($after  | Where-Object { $_.Rel -ieq $k }).Sha256
    if ($b -eq $a) { Write-Host "哈希一致 $k" } else { Write-Host "哈希变化 $k  $b -> $a" }
}

# 断言 4：不得出现任何形似备份/临时产物的文件名
$suspicious = @($after.Rel | Where-Object { $_ -match '\.(corrupt|bak|tmp|v2|old|orig)' })
Write-Host ("可疑产物数 = " + $suspicious.Count)
$suspicious | ForEach-Object { Write-Host "  [! ] $_" }
```

**通过标准**：新增路径数 = 0、消失路径数 = 0、三个关键文件哈希全部一致、可疑产物数 = 0。
`temp\` 子目录下应用运行期会正常产生缓存，允许变化；其余目录（含根目录、`images\`、`thumbs\`）一律不得新增。

| **必须为假的反向断言** | 1) 原 `vault.spv` SHA256 与字节数不变；2) 新增路径数 = 0；3) 不存在 `vault.spv.tmp`；4) 不存在被静默创建的新库（用 `NewVault!123` 无法解锁任何文件）；5) 不出现"已创建新库""旧数据已备份"这类既成事实的提示；6) 全局搜索界面文案，不存在任何可执行的"删除旧库/覆盖/重置"控件。 |

### V1B-09 出口验证：用户移走旧库后点「我已移走旧库，重试」

> 存在理由：只堵不给出路会把用户困死，用户最后只能去手工删文件（更危险）。本用例证明「禁止覆盖」与「用户能自救」可以同时成立。

| 项 | 内容 |
|---|---|
| 前置条件 | 同 V1B-08（阻断态已出现）；已用 2.3 记录基线。 |
| 操作步骤 | 1) 在阻断页点 `打开所在文件夹`；2) 把 `vault.spv` **手动移出**该目录（例如移动到桌面，不要删除）；3) 回到阻断页点 `我已移走旧库，重试`；4) 观察界面变化；5) 走完创建流程（主密码 `NewVault!123`）；6) 执行 2.4。 |
| 期望结果 | 重试后重新检测到库文件不存在，界面自然进入创建流程（不需要重启应用）；创建成功后能正常解锁并新增条目；被移走的旧文件在桌面完好无损。 |
| **必须为假的反向断言** | 1) 桌面上被移走的旧文件 SHA256 不变（程序不得"帮忙"移动或删除）；2) 创建前 `vault.spv` 不存在期间，目录中不得出现任何占位/空库文件；3) 创建动作只在用户确认后发生，重试本身不写盘（重试后立即执行一次 2.4，新增路径数应为 0，此时 `vault.spv` 仍不存在）；4) 不得在用户移走文件后自动搜索并"找回"旧库。 |

### V1B-10 Windows Hello 快速解锁入口

> 存在理由：架构师列出的入口是 7 个（本清单原有 5 个 + Windows Hello + 新建密码库）。v1 库旁边若残留 v1 时代的 `hello.blob`，Hello 路径最容易"先解 blob 再发现库不对"——顺序错了会先让用户按一次指纹，再告诉他不行。

| 项 | 内容 |
|---|---|
| 前置条件 | SnapFlow 完全退出。把 `legacy-vault-v1.spv` 复制为 `vault.spv`；**同时**保留一份 v1 时代生成的 `hello.blob`（可与 fixture 一同提供，或用 v1.1.4 绑定一次 Hello 后复制出来）。执行 2.3 记录基线（必须包含 `hello.blob` 的哈希）。 |
| 操作步骤 | 1) 启动 SnapFlow；2) 触发任一入口进入阻断态；3) 点 `使用 Windows Hello 解锁`；4) 观察是否弹出指纹/PIN 系统对话框；5) 若弹出则完成一次验证；6) 关闭卡片；7) 执行 2.4。 |
| 期望结果 | **不弹 Hello 验证框**（分类必须在 Hello 之前完成）；阻断提示与 V1B-01 逐字一致；`hello.blob` 仍在原处，未被清理、未被重建。 |
| **必须为假的反向断言** | 1) `hello.blob` 的 SHA256 与字节数不变（**重点**：不得因"库格式不对"顺手删掉或重建 Hello 绑定）；2) `vault.spv` 的 SHA256 与字节数不变；3) 新增路径数 = 0（尤其不得出现新的 `hello.blob.tmp`、`hello.blob.bak`）；4) 全程未出现系统级生物识别/PIN 对话框（若录屏或截图显示出现过，即判失败）；5) 不出现「Hello 绑定已失效」「请重新绑定」这类提示。 |

## 6. 已知限制

| 限制 | 说明 | 处理 |
|---|---|---|
| `temp\` 子目录允许变化 | 应用运行期正常产生缓存，纳入"新增文件 = 0"会误报 | 反向断言以根目录 + `images\` + `thumbs\` 为准，`temp\` 单独记录仅作参考 |
| `log.txt` 会增长 | 阻断流程本身可能写日志 | 只断言"文件存在"，不断言其哈希 |

| 扩展真机测试依赖浏览器 | 环境差异可能导致失败原因不明确 | 优先真机；脚本化命名管道方式用于定位 |
| V1B-09 会改动测试机目录 | 用例要求手动移走库文件 | 执行后用备份目录还原，或整机快照回滚 |
