## 1. 优化目标

目标必须可度量，验收时逐条打勾。

| 编号 | 目标 | 可验证口径 |
|---|---|---|
| G1 密码短语真实强度 | 密码短语不再是「看起来很长的弱密码」 | 内置 **EFF 大词表 7776 词**（log2(7776) ≈ 12.93 bit/词，CC BY 3.0，署名写入 THIRD-PARTY-NOTICES）；默认 **6 词** ≥ **77 bit**，4 词 ≥ **51 bit**；界面熵值必须由实际词表长度联动计算，不得写死常数（单测断言 `words × log2(词表大小)`，误差 ≤ 0.5 bit）；源码注释与 UI 文案中不得出现与实际不符的熵值。**备选**（仅当工程侧确实取不到 EFF 表时启用，非默认）：自建 ≥ 4096 词 + 默认词数提到 7 词 |
| G2 全字节认证 | 库文件任一字节被修改都能被发现 | 对 v2 样本做头部逐字节翻转矩阵测试（magic / version / KDF 参数 / salt / nonce 各取样点，≥ 20 处）：100% **无法解锁**，且统一落到「无法解锁密码库」这张卡片，不改写原文件；**不要求也不允许**程序进一步区分「密码错」与「文件被改」（GCM 无法区分，强行区分只能靠泄漏内部信息）；头部被伪造成 v1 时返回「格式不支持」而非解密出内容 |
| G3 内存零残留 | 锁定后不留下可被内存 dump 提取的密钥材料 | 主密码字节、派生密钥、wrapKey、明文载荷字节、备份密钥、签名缓冲在离开作用域时立即清零；「解锁 → 操作 → 锁定」完整周期后，Debug 版残留检测断言全部通过 |
| G4 UI 不阻塞 | 任何单个操作的主线程阻塞 < **50ms** | 改主密码（页面显示进度）、保存、CSV 导入 5000 条、体检计算 5000 条：主线程阻塞均 < 50ms（用 UI 响应性埋点验证） |
| G5 数据不可丢 | 任何异常路径下用户库文件 0 丢失 | 保存失败可回退到上一版本（滚动备份 ≥ 1 版）；v1 旧库 0 次自动删除/覆盖；解析失败产生的备份文件数量有上限 |
| G6 可维护 | 解锁/列表/编辑器/生成器/动态验证码/导入导出不再挤在一个类里 | `PasswordWindow.xaml.cs` 从 1849 行降到 **< 600 行**，每个子视图职责单一；重构前后既有约 130 个测试全绿、界面行为无回归 |

## 2. 用户故事

### 2.1 普通用户（存几十个网站密码）

| # | 故事 | 验收标准 |
|---|---|---|
| U1 | 作为普通用户，我想一键生成一个记不住的强密码，这样我就不用自己想 | 默认 6 词产出 ≥ 77 bit 熵的密码短语；界面明确展示「≈ XX bit」；点击即可填入并可复制 |
| U2 | 作为普通用户，我误删了一条我想恢复 | 删除后立即出现「已移到回收站 · 撤销」提示，点击撤销恢复原位；30 天内在回收站可恢复 |
| U3 | 作为普通用户，我想知道哪些密码该换了 | 打开「密码体检」看到汇总条与问题分组，每条问题能一键跳到对应条目处理；体检在本机完成、有明确说明不上传 |
| U4 | 作为普通用户，我改错了密码想回到上一个 | 详情页可查看最近 5 次变更并回滚，回滚前有确认提示 |
| U5 | 作为普通用户，我改主密码时界面不能卡死 | 改主密码时界面保持可交互，有进度文案，可取消（取消后库内容与主密码保持原状） |

## 4. 新增功能详述

### 4.1 密码体检（UX-02）

**检测维度**

| 维度 | 判定规则（阈值已定，见第 8 章 Q5~Q7、Q15） | 单条处理动作 |
|---|---|---|
| 重复密码 | 同一密码出现在 ≥ 2 个登录条目 | 展开该组，逐条跳转改密码（可标记「这是我有意复用」，本次会话不再提示） |
| 弱密码 | 实际熵 < **50 bit** 或长度 < **10** 或仅单一字符类 | 跳转条目并打开生成器预填 |
| 密码包含标题或用户名片段 | 密码中出现条目标题、用户名（忽略大小写、忽略分隔符、长度 ≥ 4 的片段） | 跳转条目并打开生成器预填（与弱密码同组统计，单独打标签） |
| 长期未更新 | `UpdatedUtc` 超过 **365 天** | 跳转条目，用户可「标记为已知无需修改」 |
| 关键账号未开两步验证 | 条目「登录」类、有网址且命中内置关键词表（银行、支付、邮箱、云服务、社交与内容社区、政务与社保、企业办公 共 7 组 73 条，见 `04-critical-keywords.md`）或用户手动标记为关键账号，且 `TotpSecret` 为空 | 跳转条目并聚焦 动态验证码 输入框，附「如何获取 Base32 密钥」说明 |

明确**不做**：已知泄露密码库比对（需联网，与「数据仅存本机」冲突）、跨用户统计、任何上传。

**呈现方式**

- 入口：左侧筛选区（全部 / 登录 / 笔记 / 验证码 之后）新增「**体检**」，右侧显示未处理问题数徽章。
- 顶部汇总条：`共 12 个条目需要处理` + 五个维度计数，颜色按严重度分级（弱密码/重复最高）。
- **计数口径（必须与文案一致）**：五个维度计数**各自独立、互不包含**（`弱密码` 不含 `密码含名称` 的条目）；汇总条的总数按**条目去重**的并集计算，因此**不等于五组之和**。同一账号可以同时出现在多个分组里，这是正常的。
- 主体：按维度分组的手风琴列表，每组展开是条目行（标题 + 用户名 + 问题标签），点行直接跳到该条目详情并高亮问题字段。
- 空状态：`没有发现问题。` + `建议每月检查一次。`
- 隐私说明常驻底部小字：`体检只在本机进行，不会上传你的密码。`

**性能预算**：5000 条首次计算 < 300ms，增量（单条修改后）< 5ms；计算在后台线程，结果按「库版本号 + 条目修改时间」缓存，解锁不自动全量重算（首次进入体检页时算）。

### 4.2 回收站（UX-03）

| 项 | 规格 |
|---|---|
| 删除行为 | `Del` 或删除按钮 → 条目移动到回收站（记录删除时间、原位置排序键），**不再弹「删除后无法恢复」**；先给 6 秒「已移到回收站 · 撤销」提示，撤销即原位恢复 |

| 恢复 | 单条「恢复」回到原分类与原排序位置；若原条目 ID 已被占用则作为新条目恢复并提示 |
| 彻底删除 | 单条「彻底删除」需二次确认；「清空回收站」需输入一次主密码（防误触） |
| 范围隔离 | 回收站条目**不参与**：列表 / 搜索 / 体检 / 浏览器扩展匹配与自动填充 / 明文 CSV 导出 / 计数徽章；**参与**：加密备份（作为独立区段一并备份，恢复时按备份中的回收站状态还原） |
| 机密策略 | 回收站中的条目沿用原有防截屏与机密剪贴板规则；密码字段默认掩码显示 |

## 5. 库格式 v2 规格要求（产品视角）

| 编号 | 要求 | 说明 |
|---|---|---|
| F1 | 版本号显式存在于头部，且**自身被认证** | 版本号在被篡改时不得让格式判定漂移；v1 头不得被当作 v2 解析 |
| F2 | AAD 覆盖全部头部字段 | magic、版本号、KDF 算法标识与全部参数、salt、nonce、载荷长度/条目数（若写入头部） |
| F3 | 抗降级 | 头部的算法标识与参数不允许被替换成弱值后仍解密成功；任何参数变化都导致认证失败 |
| F4 | 载荷结构前向兼容 | 载荷内含明确 schema 版本与预留区（回收站、历史），新增字段不需要再升格式版本（对应 ROB-09） |
| F5 | 不做 v1 兼容 | v1 文件一律拒绝，不做自动迁移、不猜测、不尝试部分解密；五个入口（主窗口 / 热键 / 托盘 / 扩展桥 / 备份恢复）返回同一状态与同一文案 |
| F6 | 非破坏性 | 检测、拒绝、失败、升级参数等所有路径都不删除、不覆盖、不重命名用户库文件；不得生成 `.corrupt-*`、`.bak`、`.tmp`、`.v2` 等自动产物（ROB-01 的限量备份属于唯一例外） |
| F7 | 未知更高版本 | 遇到高于当前支持的版本号，提示「此密码库由更新版本的 SnapFlow 创建」并只读保留文件 |

**用户文案（v1 旧库，原文）**

- 标题：`无法打开这个密码库`
- 正文：`当前密码库由旧版本 SnapFlow 创建，本版本已升级为新的加密格式，无法直接打开。你的库文件完整保留在：{路径}。请先自行备份这份文件，再用旧版本 SnapFlow 导出数据，然后在本版本新建密码库并导入。我们不会删除或覆盖你的库文件。`
- 按钮：`打开所在文件夹` / `我已移走旧库，重试`
- 副提示（可展开）：`建议先复制一份库文件再做任何操作。旧版本安装包不随本版本提供，请从你原先的下载渠道获取。`
- **阻断页不提供任何删除、覆盖、重建、重置按钮**，只能关闭窗口；程序内不存在任何可覆盖该文件的路径。

**用户文案（新建密码库入口在 v1 存在时被点击，原文）**

- 标题：`无法创建新的密码库`
- 正文：`当前目录已有旧版本密码库，请先备份并移走后再创建。`
- 按钮：`打开所在文件夹` / `关闭`
- 说明：该入口**保持可见但不可执行**——点击必须给出这条提示，不允许静默禁用（静默禁用会让用户以为程序坏了）。

> **口径理由（写入文档以备后续争议）**：v1 库读不出来，就意味着无法"先在程序内导出数据再覆盖"。因此任何形式的覆盖都等于**无备份销毁**，不存在可接受的二次确认能弥补。禁止覆盖 + 提供「我已移走旧库，重试」出口，是唯一自洽的组合。

**用户文案（主密码不正确 / 库损坏 / 头部被篡改 —— 同一张卡，原文）**

> **为什么合并**：AES-GCM 的 tag 失败在密码学上无法区分「密码输错」与「文件被改」，两者都只是 tag 不匹配。因此不做两套文案，也不允许程序进一步区分原因（详见 G2、U6）。结构性损坏（截断、坏 magic、参数越界）在派生密钥前即可分类，但用户侧同样落到这张卡，无需区分。

**固定结构（五行，不要合并成一段）**：

| 位置 | 内容 |
|---|---|
| 标题 | `无法解锁密码库` |
| 正文 | `主密码不正确，或这个密码库已损坏／被修改。` |
| 路径行 | `文件保存在：{path}`，右侧 `打开所在文件夹`（路径文本可选中复制） |
| 辅助行 | `如果确认主密码无误，可从加密备份恢复。` |
| 按钮 | `重试`（默认） / `用备份文件恢复` / `关闭` |

**`重试` 的行为（写清楚，避免实现跑偏）**：清空密码框、聚焦密码框、停留在当前页，**不重新读盘、不重新校验文件头、不触发 Hello 验证**。只有用户再次提交时才重新走一次完整解锁。

**用户文案（更高版本，原文）**

- 标题：`密码库版本过新`
- 正文：`此密码库由更新版本的 SnapFlow 创建，请升级 SnapFlow 后再打开。文件已保持不变。`

## 7. 优先级与里程碑建议

三个批次各自可独立验收、独立合并，不互相阻塞。

| 批次 | 主题 | 包含需求 | 独立验收口径 | 相对工作量 |
|---|---|---|---|---|
| **A 安全底线** | 格式 v2 + 真实性 + 不丢数据 | SEC-01、SEC-02、SEC-03、SEC-04、ROB-01、ROB-09 | 篡改矩阵 100% 拦截；**五个入口**遇 v1 均阻断且文件哈希不变、无自动产物；清零断言通过；EFF 词表熵断言（6 词 ≥ 77 bit）通过；备份去重生效；预留字段就位 | 中 |
| **B 健壮与性能** | 卡顿、写坏、并发、限流 | ROB-02 ~ ROB-08 | 主线程阻塞 < 50ms、改主密码可取消且原文件完好；滚动备份 3 份可回退；并发配对只成功 1 个；60 次/分钟限流生效、审计 200 条不落盘；导入 5000 条 < 1s，三类超限（条目/字段/文件）均整体拒绝且库哈希不变 | 中 |
| **C 体验与新功能** | 拆分 + 体检 + 回收站 + 历史 | UX-01（先做）、UX-02、UX-03、UX-04 | 主文件 < 600 行且零回归；体检五维度 < 300ms 且可处理到底；回收站 30 天/500 条先进先出、不参与搜索与扩展匹配、进备份不进明文导出；历史 5 版可回滚 | 大 |

**排序理由**

1. 批次 A 先做，因为格式一旦定稿再改要二次破坏用户数据；ROB-09 的预留字段必须在 A 里定，否则批次 C 会触发 v3。
2. 批次 B 与 C 可并行推进（改动的文件几乎不重叠），但 UX-01 必须排在 C 的功能之前，避免同一巨型文件改两遍。
3. 批次 A 上线即产生**用户可见的破坏性变化**（旧库打不开），必须与提示文案、帮助说明、发布说明同步交付。

**风险提示**

| 风险 | 影响 | 缓解 |
|---|---|---|
| v2 不做 v1 兼容，老用户升级后打不开库 | 高（用户感知为「数据丢失」，虽然文件完好） | 发布说明置顶迁移指引；五个入口统一阻断并给出完整路径与自行备份后重建的指引；**不随包附带旧版安装包**（已决 Q9），文案指引用户从原下载渠道获取旧版 |
| 历史与回收站放大库体积 | 中 | 历史上限 5 版、回收站上限 500 条；备份体积上限需评估 |
| 体检阈值定得过严造成提示疲劳 | 中 | 阈值可配置，允许「标记为已知」，默认只显示高严重度 |
